# 性能实现与验收

计时分清引擎、IPC、JS、下一rAF和物理呈现。局部微基准不推导整体加速比例；本轮未证明全部P95达标。

## 已实施

- Office原子inspect、轻量选区、交互优先与可替代读取合并；内部可绘制状态不再被同版本公开withdrawn回执覆盖，消除已定位的2500ms心跳等待。遥测不能阻断有效呈现。
- 大Office辅助模型进入有界Worker；ZIP目录同时估计展开XML，避免高压缩大正文漏判。空闲按格式load、initialize、首瓦片、close预热，阶段间让路，已执行的LO调用不可抢占。
- Markdown明确范围的巨行普通输入、可视装饰、有界fragment和纯文本扫描；分栏直接消费Text/ChangeSet。快速Undo保序，迟到回流保留新Range。
- 浮栏不携全文；光学纹理计算/编码进入Worker，合并几何读取，长任务期间降低材质成本。
- 大正文编码/摘要、patch指纹和恢复导出进入有界Worker；blob/delta、逆操作、快照及回执准入减少重复复制。完整Markdown导出移至隔离renderer，流式复制媒体。

## Markdown实绩与限制

TxHN2y：i7-13700/32GiB、1440×900 DPR1，每组100次，beforeinput→下一rAF，单位ms。

| 文档/模式 | P50 | P95 |
| --- | --- | --- |
| 1MiB分栏 | 3.0 | 7.1 |
| 10MiB阅读/分栏 | 2.2/3.1 | 7.6/326.7 |
| 10MiB巨段源码/阅读/分栏 | 15.9/16.6/43.4 | 727.6/347.9/367.9 |

文档焦点均为true，但Windows前台仍为LockApp；出现无对应JS长任务的帧调度空档，不能当作交互桌面验收或物理paint。巨段分栏确有同步双解析成本，最长JS任务51ms，不能全部归因锁屏。64KiB以上采用独立字符扫描与URL缓存，12103个语义对照一致；Node巨段微基准P50 22.32→18.19ms，仅说明解析器局部收益。

mR7NRz各10次真实浮栏点击：阅读/分栏到回执P95 186.2/177.3ms，到源校验rAF 187.2/556.6ms；选区回复约1.8KiB，不携10MiB正文。样本数小，帧长尾保留。

## 后续验收与顺序

1. 解锁桌面后复测真实WeType与帧时延；每交互≥100次、打开≥10次，分别报告冷/热、P50/P95、排队和呈现。目标输入≤50ms、选区≤100ms、格式≤200ms，1/10MiB输入≤50/100ms，小Office冷/热≤5/1.5s。
2. 优先消除巨段双解析及fragment切片成本，保留完整语法、Range和即时Undo；再拆分Core/App会话、命令和视图服务。首次blob冻结/差分与部分metadata JSON仍在main。
3. 连续开关20次，记录进程树CPU/private bytes、队列、会话和监听器；JS heap不等于总内存。证据留TEMP，不把模拟或隐藏引擎当真实桌面。
